MEGA-MANUTENÇÃO DO FLUXO DE CADASTRO — SISTEMA PROTE ADM
Projeto: PROTE — Sistema administrativo de transporte escolar
Equipe: LIAME
Arquivo de contexto para retomada futura

1. CONTEXTO GERAL

O sistema PROTE ADM está passando por uma manutenção urgente no fluxo de cadastro originado por orçamentos e também no fluxo manual de cadastro de responsáveis.

O problema central identificado é que o fluxo atual está confuso e quebrado porque mistura criação automática de dados no backend, uso de localStorage no frontend, vínculo por nomes em vez de IDs, ausência de campos adequados na entidade orçamento e falta de controle correto do estado do orçamento durante a conversão.

A regra nova definida para o sistema é:

- Um orçamento convertido deve gerar um novo responsável.
- Depois do responsável, o sistema deve cadastrar aluno e mensalidade individualmente.
- O fluxo correto para orçamento com vários alunos é:
  orçamento -> responsável -> aluno 1 -> mensalidade 1 -> aluno 2 -> mensalidade 2 -> ... -> último aluno -> última mensalidade -> alert de sucesso.
- A mensalidade é individual por aluno, pois cada aluno pode ter um preço próprio.
- O valor da mensalidade começa vazio. Quem define o valor é o condutor.
- O orçamento não terá dados do aluno, apenas dados do responsável e quantidade de alunos.
- O orçamento só será considerado convertido depois que todo o fluxo terminar.
- O cadastro manual de responsável continua existindo e deve seguir o mesmo fluxo:
  responsável -> aluno -> mensalidade.
- No cadastro manual de responsável, o campo quantidade de alunos existe e deve ser obrigatório.
- O sistema não deve depender de localStorage para controlar fluxo de cadastro.
- O sistema deve usar IDs reais do banco e requisições fetch para manter a integridade dos dados.
- Não pode haver alteração visual no projeto sem autorização.
- Alterações no frontend devem ser limitadas a arquivos JavaScript necessários para fetch, redirecionamento e funcionamento dos formulários.
- Não mexer em CSS, layout, estrutura visual, ícones ou design sem permissão explícita.

2. DECISÕES JÁ TOMADAS

2.1 Status do orçamento

O enum de status do orçamento deve ser alterado no backend e no banco de dados.

Status recomendados e aprovados:
- PENDENTE: orçamento recebido, ainda não iniciado.
- EM_CADASTRO: orçamento iniciou o processo de conversão, mas ainda não terminou responsável, aluno(s) e mensalidade(s).
- CONVERTIDO: orçamento concluiu todo o fluxo e virou cliente operacional.
- RECUSADO: orçamento recusado.

A alteração deve ocorrer no banco MySQL e também no model TypeORM, pois mudar apenas o backend não basta. O MySQL rejeitaria valores novos se o ENUM da tabela continuasse antigo.

2.2 Campo nome_cliente

O campo nome_cliente da entidade orçamento é ambíguo e deve ser substituído por nome_responsavel.

Motivo:
- O orçamento não deve armazenar nome de aluno.
- O orçamento representa a solicitação inicial feita por um responsável.
- O campo nome_cliente gera confusão entre cliente, responsável e aluno.
- A documentação e o código atual ainda usam nome_cliente, então a manutenção deve corrigir banco, model, service e JavaScript que usam esse campo.

2.3 Quantidade de alunos no orçamento

A tabela orçamento já possui quantidade_alunos, mas a tela de orçamento não exibe esse campo atualmente.

Isso é um problema, porque o fluxo depende desse número para saber quantas vezes repetir aluno -> mensalidade.

Como o frontend precisará ser ajustado, será necessário pedir permissão específica antes de alterar o formulário da tela de orçamento, pois adicionar input em HTML é alteração de frontend. Porém, sem esse campo, orçamento sempre tende a cair no padrão atual de 1 aluno.

2.4 Valor do orçamento

Por enquanto, o campo valor do orçamento será ignorado na manutenção.

Motivo:
- Existe divergência de opinião na equipe sobre ele.
- Um parceiro responsável pelo banco considera que orçamento deve ter valor.
- O fluxo de mensalidade não usará esse valor como sugestão.
- A mensalidade começará vazia e será definida pelo condutor.

2.5 Rota de orçamento

A rota atual /orcamentos/:id/aprovar deve ser substituída por uma lógica com nome mais claro, preferencialmente /orcamentos/:id/converter.

Motivo:
- O termo aprovar gera confusão.
- Quem aprova o orçamento é o cliente via WhatsApp.
- No sistema administrativo, o condutor converte o orçamento em cadastro operacional.
- O botão visual pode continuar com o mesmo texto por enquanto para evitar mexer em visual, mas a rota e a lógica do backend devem usar "converter".

2.6 Email e endereço do responsável

Email do responsável:
- Deve ser opcional no banco.
- Deve ser opcional no backend.
- Deve ser opcional no frontend.

Endereço do responsável:
- Deve ser obrigatório.

2.7 Alert final

Ao finalizar todo o fluxo, tanto vindo de orçamento quanto de cadastro manual, o sistema deve exibir:
"Novo cliente cadastrado com sucesso!"

Esse alert deve aparecer depois da mensalidade do último aluno.

4. MANUTENÇÕES NO BANCO DE DADOS

4.1 Alterar enum de status do orçamento

A tabela orçamento deve permitir os seguintes status:
- PENDENTE
- EM_CADASTRO
- CONVERTIDO
- RECUSADO

Motivo:
O orçamento não deve virar convertido no momento em que o condutor inicia o processo. Ele só vira convertido ao final do cadastro completo.

4.2 Trocar nome_cliente por nome_responsavel

A tabela orçamento deve substituir o campo nome_cliente por nome_responsavel.

Motivo:
O orçamento guarda dados do responsável e quantidade de alunos, não dados individuais dos alunos.

Atenção:
- Ajustar script SQL.
- Ajustar inserts, se existirem.
- Ajustar model TypeORM.
- Ajustar service de orçamento.
- Ajustar frontend JS que envia ou lê nome_cliente.

4.3 Conferir quantidade_alunos

A coluna quantidade_alunos deve continuar existindo e deve ser essencial no fluxo de orçamento.

Motivo:
O sistema usa esse número para repetir aluno -> mensalidade.

4.4 Conferir email do responsável

Email deve ser opcional. Se a coluna estiver NOT NULL, deve ser alterada para aceitar NULL.

4.5 Conferir endereço do responsável

Endereço deve ser obrigatório. Se a coluna estiver permitindo NULL indevidamente, avaliar correção.

4.6 Não adicionar id_orcamento em responsável por enquanto

Após esclarecimento do usuário, responsável não precisa obrigatoriamente nascer de orçamento, pois também existe cadastro manual.

Portanto:
- Não adicionar id_orcamento obrigatório em responsável.
- Se a equipe quiser rastreabilidade futura, poderia ser opcional, mas não é necessário para esta manutenção.

5. MANUTENÇÕES NO BACKEND

5.1 service_orcamento.ts

Problema atual:
O service de orçamento aprova e já cria responsável, aluno e mensalidade automaticamente.

Nova regra:
Converter orçamento deve apenas iniciar o processo.

Comportamento esperado:
- Receber id_orcamento.
- Buscar orçamento.
- Validar se existe.
- Validar se está PENDENTE.
- Alterar status para EM_CADASTRO.
- Manter convertido como false.
- Salvar.
- Retornar orçamento atualizado para o frontend.

Não deve:
- Criar responsável.
- Criar aluno.
- Criar mensalidade.
- Usar nome "XXXXX" para aluno.
- Finalizar orçamento antes da hora.

5.2 Controller e routes de orçamento

renomear rota aprovar para:
PUT /api/orcamentos/:id/converter

Essa rota deve chamar o service de conversão/início de cadastro.

A rota antiga /aprovar pode ser removida ou mantida temporariamente redirecionando para a nova lógica, dependendo do risco de quebra. Porém, o ideal é migrar o frontend para a rota /converter.

5.3 service_responsavel.ts

Regras:
- Responsável manual pode ser cadastrado normalmente.
- Responsável vindo de orçamento deve ser criado a partir dos dados revisados.
- Email opcional.
- Endereço obrigatório.
- Quantidade de alunos obrigatória no fluxo manual e útil no fluxo de orçamento.

Ao salvar responsável:
- Retornar id_responsavel.
- O frontend usa esse ID para cadastrar aluno.
- Não depender de nome para vínculo.

5.4 service_aluno.ts

Regras:
- Aluno deve ser cadastrado usando id_responsavel.
- O service deve validar se o responsável existe.
- Não buscar responsável pelo nome.
- Ignorar campo de horário/turma neste momento.
- Retornar id_aluno criado.

5.5 service_mensalidade.ts

Regras:
- Mensalidade deve ser cadastrada com id_aluno.
- Validar se o aluno existe.
- Valor é obrigatório e definido pelo condutor.
- Mensalidade é individual por aluno.
- Depois de salvar a mensalidade, o sistema decide se deve ir para o próximo aluno ou finalizar.

5.6 Finalização da conversão

Ao terminar a mensalidade do último aluno de um orçamento:
- Alterar status do orçamento para CONVERTIDO.
- Alterar convertido para true.
- Definir data_conversao, se existir esse campo.
- Retornar sucesso para o frontend.
- Frontend exibe alert.

6. CORREÇÕES DE FLUXO DE FORMULÁRIOS

6.1 Fluxo vindo de orçamento

Fluxo obrigatório:
1. Tela de orçamento: usuário clica para converter.
2. Backend muda orçamento para EM_CADASTRO.
3. Frontend redireciona para:
   responsaveis.html?fluxo=orcamento&id_orcamento=ID
4. Tela de responsável busca orçamento por ID.
5. Formulário de responsável é preenchido com os dados do orçamento.
6. Usuário revisa e salva responsável.
7. Backend cria responsável e retorna id_responsavel.
8. Frontend redireciona para:
   alunos.html?fluxo=orcamento&id_orcamento=ID&id_responsavel=ID&alunoAtual=1&totalAlunos=N
9. Usuário cadastra aluno 1.
10. Backend cria aluno e retorna id_aluno.
11. Frontend redireciona para:
    mensalidade.html?fluxo=orcamento&id_orcamento=ID&id_responsavel=ID&id_aluno=ID_ALUNO&alunoAtual=1&totalAlunos=N
12. Usuário cadastra mensalidade 1.
13. Se alunoAtual < totalAlunos:
    redirecionar para próximo aluno:
    alunos.html?fluxo=orcamento&id_orcamento=ID&id_responsavel=ID&alunoAtual=2&totalAlunos=N
14. Se alunoAtual == totalAlunos:
    backend finaliza orçamento como CONVERTIDO.
    frontend exibe alert "Novo cliente cadastrado com sucesso!".
    redirecionar para uma tela definida pela equipe, provavelmente orçamentos, responsáveis ou dashboard.

6.2 Fluxo manual de responsável

Fluxo obrigatório:
1. Usuário abre responsaveis.html.
2. Cadastra responsável manualmente.
3. quantidade_alunos deve ser obrigatória.
4. Backend cria responsável e retorna id_responsavel.
5. Frontend redireciona para:
   alunos.html?fluxo=manual&id_responsavel=ID&alunoAtual=1&totalAlunos=N
6. Usuário cadastra aluno 1.
7. Vai para mensalidade 1.
8. Repete aluno -> mensalidade até o último aluno.
9. Ao final, exibe alert "Novo cliente cadastrado com sucesso!".

6.3 Controle por query params

Evitar localStorage no fluxo.

Parâmetros úteis:
- fluxo=orcamento ou fluxo=manual
- id_orcamento
- id_responsavel
- id_aluno
- alunoAtual
- totalAlunos

O frontend deve usar esses parâmetros para buscar dados no backend e decidir o próximo passo.

7. CORREÇÕES NO FRONTEND

Regra geral:
Não alterar visual sem autorização.

Permitido:
- Alterar JavaScript para fetch.
- Alterar JavaScript para redirecionamento.
- Alterar JavaScript para preenchimento automático de campos já existentes.
- Alterar JavaScript para remover dependência de localStorage.
- Alterar HTML apenas se for tecnicamente obrigatório, e antes pedir permissão.

Não permitido sem autorização:
- CSS.
- Layout.
- Ícones.
- Cores.
- Design.
- Reorganização visual.
- Mudança de texto visível que não seja necessária.
- Troca visual de botão.

7.1 orcamento.js

Alterações necessárias:
- Trocar chamada da rota aprovar para converter.
- Após resposta do backend, redirecionar para responsaveis.html com id_orcamento.
- Não mostrar sucesso final nesse momento, pois o cliente ainda não foi cadastrado.
- Não depender de localStorage.

Possível necessidade de HTML:
- A tela de orçamento atualmente não exibe quantidade_alunos.
- Será necessário pedir permissão antes de adicionar input no formulário, pois isso mexe em HTML.

7.2 responsaveis.js

Alterações necessárias:
- Ler query params.
- Se fluxo=orcamento, buscar orçamento por id_orcamento.
- Preencher campos existentes com dados do orçamento.
- Exigir quantidade_alunos.
- Ao salvar, receber id_responsavel.
- Redirecionar para alunos.html com fluxo, id_responsavel, alunoAtual e totalAlunos.
- Email opcional.
- Endereço obrigatório.

7.3 alunos.js

Alterações necessárias:
- Ler id_responsavel, fluxo, alunoAtual e totalAlunos.
- Salvar aluno usando id_responsavel.
- Não buscar responsável por nome.
- Ignorar horário/turma.
- Após salvar aluno, redirecionar para mensalidade do aluno criado.
- Não depender de localStorage.

7.4 mensalidade.js

Alterações necessárias:
- Ler id_aluno, fluxo, alunoAtual e totalAlunos.
- Criar mensalidade para id_aluno.
- Valor começa vazio e deve ser informado pelo condutor.
- Após salvar:
  - Se ainda houver aluno pendente, redirecionar para próximo aluno.
  - Se for o último aluno e fluxo=orcamento, chamar finalização do orçamento.
  - Se for o último aluno e fluxo=manual, apenas exibir alert final.
- Não depender de localStorage.

9. ALERTAS DE RISCO

9.1 Risco ao alterar ENUM

Alterar ENUM no MySQL exige cuidado, pois dados existentes precisam continuar compatíveis.

9.2 Risco ao renomear nome_cliente

Renomear coluna pode quebrar:
- Model TypeORM.
- Services.
- Controllers.
- Scripts SQL.
- Inserts.
- Frontend JS.
- Busca/listagem de orçamentos.

Antes da alteração, procurar todos os usos de nome_cliente no projeto.

9.3 Risco no frontend

Mesmo sem mexer no visual, alterar JS pode mudar comportamento.
Fazer backups ou commits antes de cada etapa.

9.4 Risco de fluxo incompleto

Se o usuário abandonar o fluxo no meio, o orçamento ficará EM_CADASTRO.
Isso não é erro, mas precisa ser entendido. Futuramente pode haver botão "continuar cadastro".

11. RESUMO EXECUTIVO

A manutenção deve resolver a raiz do problema: o sistema não pode mais tentar converter orçamento automaticamente em responsável, aluno e mensalidade sem revisão.

A partir de agora, orçamento inicia um fluxo guiado. O backend controla os estados e a integridade. O frontend apenas conduz o usuário entre os formulários usando IDs reais do banco.

A prioridade máxima é corrigir banco e backend antes de mexer nos JS. O frontend só será alterado no comportamento necessário para fetch e redirecionamento, sem alterações visuais.

Fluxo final desejado:
- Orçamento: converter -> responsável -> aluno 1 -> mensalidade 1 -> aluno 2 -> mensalidade 2 -> final.
- Manual: responsável -> aluno 1 -> mensalidade 1 -> aluno 2 -> mensalidade 2 -> final.

Mensagem final:
Novo cliente cadastrado com sucesso!
